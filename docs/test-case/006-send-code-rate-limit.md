验证验证码发送频率限制，以 HTTP 响应和后续查询作为判定依据。

### 本用例附加条件

冷却时间直接取第一次 HTTP 响应的 next_send_after；只有自然等待与请求重试，不读取或更改限流配置。

## 接口调用步骤

### 步骤 1

```http
POST {{BASE_URL}}/auth/send-code
Accept: application/json
Content-Type: application/json

{
  "identityType": "email",
  "identityValue": "782213745@qq.com",
  "purpose": "register"
}
```

保存 data.next_send_after 为 WAIT 秒。

### 步骤 2

在 WAIT 秒内立即再次执行下面请求。

### 步骤 3

```http
POST {{BASE_URL}}/auth/send-code
Accept: application/json
Content-Type: application/json

{
```

### 步骤 4

从第一次响应取得 WAIT，真实等待至该冷却期结束后再次提交同一请求。

## 期待结果

- 所有响应包含 `code`、`message`、`data`、非空 `requestId`；成功按 OpenAPI 为 HTTP 200、`code=0`。失败不泄露堆栈或凭证明文。
- 各步骤先核对其预期再继续；准备请求失败或变量无法取得时停止并记录阻塞，行为与预期不符时记录失败。
- 仅判定本文件 HTTP 请求可以观察的结果；没有 HTTP 查询能力的内部存储、广播、日志等项目不计为已验证。
- 首次和冷却结束后的调用成功；冷却期内 HTTP 429、code=42901，并返回可据以等待的时间信息。
- 限流请求应明确失败；恢复时间以 HTTP 返回的等待信息为准。HTTP 未提供投递明细，实际发送次数不在本用例可验证范围。
