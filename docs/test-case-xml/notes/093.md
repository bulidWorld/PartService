# TC-093 转换说明

- 来源：`docs/test-case/093-chat-read-position.md`。生成独立同 stem XML；社区从本文件 GET /communities 提取，注册 A/B、A 创建主题并邀请 B、B 接受生成 ROOM、A 发送消息 M，最后 B 成员调用 POST /rooms/{roomId}/read 写入 lastReadMessageId=M。
- 逐步骤转换：步骤 1-3 同 092（社区准备 + 双身份注册并提取 USER/TOKEN/REFRESH 及原始令牌副本）；步骤 4-7 依次创建主题 T、邀请 I、接受取得 ROOM（校验非空 UUID）、发送消息 M；步骤 8 为标记已读写入。每个 REST 显式 auth、Accept/Content-Type、真实 HTTP 状态与业务码断言，准备失败 raise Blocked 并保留 finally 清理；依赖前序提取的前置步骤均带 ifParameter + onFalse="blocked"。
- 目标断言（可表达部分）：POST /rooms/{roomId}/read 的写入响应断言 HTTP 200/code=0、requestId 非空、data.roomId=ROOM、data.lastReadMessageId=M（ReadPosition 契约字段），与源用例期待结果一致。
- 业务接口缺口（阻塞项）：Room 模型仅含 id/topicId/ownerId/members/createdAt，不含已读位置；公开 HTTP 没有已读位置查询接口。回显不能证明已读状态已持久化，数据库/日志/内部存储不在可验证范围内。按 092 惯例，在最后一步完成写入契约断言后显式 raise Blocked 并写明原因，将持久化核查记为阻塞，不把部分覆盖记为整例通过；没有虚构查询接口。
- XML 格式无法表达：无。本用例为线性 HTTP 步骤，XSD 均可表达；阻塞结论借助 assertionCode 内的 raise Blocked 表达。
- finally 按源文档顺序清理 B/A（只清理本用例实际创建的用户）：先 GET /me 探测（200/code=0 且 data.id 匹配，或 401/code=40101 则先 POST /auth/refresh 并以 updateParam 更新当前 TOKEN/REFRESH），再 DELETE /me 断言 200/code=0/data={}/requestId 并提取业务码与 requestId 用于记录，随后用原始及当前访问令牌 GET /me、原始及当前刷新令牌 POST /auth/refresh，逐一断言 HTTP 401/code=40101。每步带 ifParameter 条件，单步失败不阻断其他用户清理；不能凭令牌失效推断注销成功。
- 共享邮箱/手机号须串行执行。单 XML 不能控制清理失败时跨任务停调度；调度方须在清理失败/未确认时停止环境复用和后续任务。执行记录保存脱敏 HTTP/业务码与 requestId，不记录令牌原文。
- 仅生成；未执行 HTTP、部署或数据库操作。XSD/语义及真实导入器离线校验结果见交付简报。
