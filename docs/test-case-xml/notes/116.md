# TC-116 转换说明

- 来源：`docs/test-case/116-rating-summary-counts.md`。独立查询社区与评价分类（需 average/no_show/reliable），注册 A（email 782213745@qq.com）与 B（phone 13900000002），A 依次创建三个主题并邀请 B、B 接受产生非空 UUID 聊天室，A 分别提交 good（["reliable"]）、neutral（["average"]）、bad（["no_show"]）三条评价，随后 B 查询 `/me/rating-summary` 断言计数与比率。
- 请求与响应字段以 `rest-api/ratings.yaml` 为准：`POST /topics/{topicId}/ratings`（bearer）响应 data 为 Rating（id/topicId/fromUserId/toUserId/score/categories/comment/createdAt）；`GET /me/rating-summary`（bearer）响应 data 为 RatingSummary（good_count/neutral_count/bad_count/total_count/risk_tags 必填，good_rate/bad_rate 为可空 number）。
- 步骤转换要点：步骤 1、2 为公开准备请求，社区不足或缺少 average/no_show/reliable 分类均 raise Blocked（无公开创建社区/分类接口）。注册 A/B、创建主题 T/T2/T3、邀请、接受与三次评价提交均为准备请求，失败 raise Blocked，断言失败仍提取 user.id/accessToken/refreshToken 供 finally 清理；三次评价响应核对 topicId、fromUserId=USER_A、toUserId=USER_B、score/categories 与提交一致。共同参与者身份通过 A 创建主题、邀请 B、B 接受产生非空 UUID roomId 建立，仅 HTTP 可观察，不推断内部参与存储。
- 目标断言（步骤 17）：good_count=1、neutral_count=1、bad_count=1、total_count=3 且 total_count 等于三类之和；good_rate、bad_rate 非空且与 1/3 偏差 ≤0.0001（四位小数 0.3333）；risk_tags 为数组。
- XML 格式无法表达：任务格式无轮询循环，源用例「允许轮询摘要等待异步任务」以查询前固定等待 3000ms 近似；统计完成 SLA 未约定数值，且仅公开 HTTP 可观察规则禁止用系统时钟/日志替代断言，按源用例「未约定 SLA 则阻塞时效验收」，目标步骤核查计数与比率后 raise Blocked 记录时效验收阻塞，finally 仍执行清理。
- 业务接口缺口：当前实现 `RatingsControllerImpl.getMyRatingSummary` 返回固定零值样例（0,0,0,0,[]），计数/比率断言执行时预计失败，属服务侧实现缺口；XML 仍按源用例契约断言，不修改服务代码。
- finally 顺序清理 B、A：先 GET /me 探测，40101 时 POST /auth/refresh 并 updateParam 更新当前访问/刷新凭证；DELETE /me 断言 HTTP 200/code=0/data={} 和非空 requestId，提取业务码及 requestId 用于记录；逐一核查注册原始及当前访问/刷新凭证 HTTP 401/code=40101。单步失败仍继续其他清理；401 不代表账号已删除。
- 跨任务身份互斥与清理失败停止后续用例需执行器任务组策略；共享邮箱/手机号必须串行复用，清理失败或未确认时停止环境复用，并保留各 HTTP/业务码与 requestId 脱敏记录。
- 仅生成；未执行 HTTP、部署或数据库操作。
