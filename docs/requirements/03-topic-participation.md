# 需求三：主题推送与接受参与

## 1. 目标

用户发布主题后，系统自动向同社区且满足主题约束的其他用户推送。用户自主选择接受；至少一名其他用户接受后，系统自动创建聊天室，由发布者和接受者共同参与。

## 2. 角色与权限

- 发布者：发布主题、查看参与情况、关闭主题，无需选择或指定接收用户。
- 推送接收用户：查看主题详情，自主选择接受，也可以忽略推送；未接受不产生参与关系。
- 已参与用户：进入聊天室，在满足条件后互相评价。
- 系统：自动筛选接收用户、分发主题、记录接受结果并维护聊天室成员。

## 3. 发布、推送与接受主流程

1. 发布者提交主题，服务端记录其社区快照和参与约束；此时不创建聊天室。
2. 系统异步筛选同社区且满足约束的其他用户，生成主题推送收件记录并发送通知。
3. 接收用户查看主题摘要、发布者、详情和参与约束，自主选择接受。
4. 服务端从登录身份确定接受用户，校验其为该主题的推送接收用户、当前仍属于主题社区且满足约束，并确认主题开放、未过期和账号可用。
5. 首名其他用户接受时，在同一事务中记录接受结果、创建唯一聊天室，并建立发布者和接受者的主题参与关系及聊天室成员关系；发布者为 owner，接受者为 member。
6. 后续用户接受时，记录参与关系并加入同一聊天室，不再新建聊天室。
7. 接受成功返回聊天室 ID；发布者无需再次确认。

## 4. 状态与幂等

- 推送收件记录维护已读情况及 `待接受`、`已接受`、`已失效` 等处理状态；不使用邀请实体或邀请状态。
- 未接受的推送在主题关闭或过期后不可再接受。
- 用户忽略推送不产生参与关系，也不需要单独的拒绝流程。
- 按主题和用户保证收件记录、接受记录、参与关系及成员关系唯一；自动分发重试不得重复生成收件记录。
- 同一主题只能有一个聊天室；多用户并发首次接受时，创建聊天室与加入成员必须保证事务一致性。
- 重复接受返回已有接受结果及同一聊天室 ID，不重复创建关系；主题关闭或过期后，已成功接受用户的重试仍返回既有结果，不新增参与关系。

## 5. 接口设计约束

- 发布主题使用 `POST /topics`，自动推送由系统触发，客户端无需另行调用分发接口。
- 接受主题使用 `POST /topics/{topicId}/accept`，无需邀请 ID，不允许通过请求体指定其他用户代为接受。
- 移除 `POST /topics/{topicId}/invite`，以及 `/invitations` 下的列表、接受和拒绝接口；推送查询使用主题收件语义，不再依赖 invitation 数据。
- 推送收件查询应支持分页，并返回主题标识、已读情况和处理状态，以便客户端展示待接受主题及进入已参与聊天室。

## 6. 异常流程

- 接受用户已不满足主题约束：重新校验失败，不产生参与或成员关系。
- 主题已关闭或过期：拒绝新的接受请求，不创建聊天室或新增成员。
- 用户已被封禁、离开主题社区或未收到该主题推送：不能接受该主题。
- 发布者不能接受自己的主题；聊天室在其他用户首次接受时自动包含发布者。
- 自动推送失败允许重试，不能依赖发布者手动选择用户补发。

## 7. 验收标准

- 发布主题后，所有同社区且满足约束的其他用户收到主题推送，跨社区或不匹配用户不会收到。
- 没有其他用户接受时，主题不存在聊天室。
- 首名其他用户接受后，自动创建包含发布者和接受者的聊天室。
- 后续接受者加入同一聊天室；并发接受和网络重试不会产生重复聊天室、参与关系或成员关系。
- 接受过程不需要发布者指定用户或再次批准，也不依赖邀请记录。
- 无权接受的用户不能通过修改主题 ID 或用户参数加入聊天室。
